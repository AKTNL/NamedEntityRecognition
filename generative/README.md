# 生成式 NER 链路（GPT-NER）

> 《自然语言处理》课程综合实践 · 任务一 命名实体识别 · 双范式对照的生成式分支
> 方法论文：Wang et al., **GPT-NER: Named Entity Recognition via Large Language Models**,
> arXiv:2304.10428（PDF 见 `docs/GPT-NER_生成式NER.pdf`）

---

## 1. 这条链路在做什么

把 NER 从「序列标注」改写成「文本生成」：给 LLM 一个提示，让它把句子中的目标实体用
`@@实体##` 包裹后**原样输出**，再从输出里解析回实体 span。

```
输入（提示）：任务说明 + 若干示例 + 给定句子：X\n标注句子：
模型输出   ：@@费德勒##在@@温布尔登##夺冠
解析       ：[(0,2,name), (4,8,scene)]
定位/转 BIO：B-name I-name I-name O B-scene ...
评测       ：seqeval 实体级 Micro F1   ← 与抽取式链路同一调用
```

论文三大机制，本项目全部实现：

| 机制                | 实现位置                          | 论文作用                          |
| :---------------- | :---------------------------- | :---------------------------- |
| ① `@@##` 标记伪装成生成   | `gptner_format.py`            | 让序列标注任务可套用 LLM 的生成能力         |
| ② 少样本示例检索         | `retriever.py`                | 随机 72.62 → 句子级 84.36 → 实体级 89.97 |
| ③ 自验证（幻觉过滤）      | `self_verify.py`              | 89.97 → 90.91                 |

外加一条论文没有、但本项目必须有的补充路线：

| 路线                 | 实现位置           | 为什么需要                                      |
| :----------------- | :------------- | :----------------------------------------- |
| ④ LoRA 有监督微调（SFT） | `train_lora.py` | 基座从 GPT-3(175B) 换成 1.5B 后 few-shot 效果必然很差，补一组「同目标格式 + 微调」的数字，范式对比才公平 |

## 3. 快速开始

```bash
# ① 数据转换（纯 CPU，约 1 分钟）
python generative/convert_cluener.py

# ② 冒烟测试：前 30 句 × 10 类型
```

## 4. 六个必须知道的工程决定

### 4.1 dev 侧展开全部 10 个类型，不使用类型 oracle

MRC-NER 原实现只为**句中出现过的类型**构造 query。那在测试阶段属于 oracle 信息泄漏，
会显著抬高 F1。本链路在 dev 侧对每句展开全部 10 个类型：

| 集合    | 原句数   | per-type 查询数 | 正例占比     |
| :---- | :---- | :---------- | :------- |
| train | 10748 | 17501       | 100%     |
| dev   | 1343  | 13430       | **16.5%** |

即 dev 有 **83.5% 的查询答案是「没有此类实体」**。这是 GPT-NER 在真实设定下的固有代价，
也是 4.2 存在的原因。

### 4.2 少样本示例必须正负混合

官方 `get_results_mrc_knn.py` 中有两行被注释掉的代码预留了负例检索接口
（`positive_idx=0/1`）。在 4.1 的分布下这一步是**必需**的：

> 若 8 条示例全是「含实体的正例」，模型会以为「必须标出一个」，
> 于是在 83.5% 的负例查询上疯狂过预测，精确率崩塌。

实测：加入 50% 负例后，同样 30 句子集上 Micro F1 从约 8% 提升到 20%。
用 `--neg-ratio` 控制（默认 0.5）。

### 4.3 停止条件不能只判换行

小模型的典型失效是**不换行、用空格接着写下一个示例**，写出
`标注句子：X 标注句子：Y ...` 一直续写到 max_new_tokens。
因此停止串集合为 `["\n", "\r", "给定句子：", "标注句子：", "输入：", "输出："]`。
另外 `NewlineStoppingCriteria` 每 4 步才检查一次——逐步解码整批的开销不可忽略，
最多多生成 4 个 token，由后处理截断兜底。

### 4.4 实体也必须能在原文中找到才算数

生成式特有失效是「幻觉」——输出原文中不存在的实体串。
`evaluate.py` 用 `text.find()` 在**原文**中定位，找不到即记为幻觉并丢弃，
同时单独统计幻觉率。这是保守对齐策略：若把幻觉计入 FP，等于用格式错误惩罚 F1，
会让数字不可解释。

### 4.5 中文的两处对标改造

| 官方（英文）                              | 本项目（中文）                       |
| :---------------------------------- | :--------------------------- |
| `context.strip().split()` 按空格分词     | 按**字**切分                      |
| `"@@" + " ".join(词) + "##"` 词间带空格   | 去空格                          |
| SimCSE `sup-simcse-roberta-large`   | **GTE** 中文句向量（失败则回退 BERT mean） |
| OpenAI GPT-3 API（付费）                | 本地 Qwen2.5-1.5B-Instruct    |
| 英文提示与类型描述                           | 中文模板 + 10 类中文语义描述（消歧用）        |

中文类型描述承担着关键消歧职责——CLUENER 同时有 `company` / `government` /
`organization` 三类易混类型，提示里必须点明边界，否则小模型必然串类。

### 4.6 评测口径必须桥接回 seqeval

官方 GPT-NER 用 **span 级、不含类型维度**的评测；抽取式用 **seqeval BIO 实体级 Micro F1**。
两者不可直接相减。本链路强制把生成结果转回 BIO 标签链，与 `train.py` 调用
**同一个 `f1_score`**，两范式数字才可比。

## 5. 口径声明（写报告时必须带上）

1. **基座规模差异**：论文用 GPT-3（175B），本项目用 Qwen2.5-1.5B（1.5B），
   参数量相差两个数量级。绝对 F1 显著低于论文应归因于**基座规模**，而非方法失效。
2. **两种oriacle 都未使用**：不使用类型 oracle（§4.1），也不使用 span oracle。
3. **幻觉率与格式异常率是新增指标**：这两个是生成式范式特有的失效维度，
   抽取式不存在，报告中应单独列出而非混进 F1。

## 6. 实验结果

运行 `python generative/summarize.py` 查看最新汇总表，结果 JSON 存于 `results/generative/`。

### 6.1 示例检索策略消融（前 120 句 × 10 类型 = 1200 条查询，k=8，负例 0.5）

| 检索策略            | Precision | Recall | Micro F1 | 幻觉率  | 格式异常  |
| :-------------- | :-------- | :----- | :------- | :--- | :---- |
| random          | 7.63      | 7.30   | **7.46**  | 7.2% | 45.2% |
| sentence-level  | 28.52     | 26.64  | **27.55** | 4.2% | 29.0% |
| entity-level    | 32.53     | 34.67  | **33.57** | 7.0% | 30.6% |

**结论：顺序完全复现论文**（论文用 GPT-3 得到 72.62 → 84.36 → 89.97）。
即「示例检索质量决定 GPT-NER 上限」这一核心主张，在 1.5B 本地基座 + 中文数据上依然成立。

> ⚠ 该组为控制算力统一用 `--max-new-tokens 72`（长句会被截断，拉低绝对值），
> 三档横向可比，但与 §6.2/§6.3 的绝对值不可直接相减。

### 6.2 LoRA 有监督微调（补充分支）

| 配置                     | Precision | Recall | Micro F1 | 幻觉率  | 格式异常 |
| :--------------------- | :-------- | :----- | :------- | :--- | :--- |
| LoRA 0-shot，**全量 dev** | 43.12     | 40.17  | **41.59** | 0.2% | 0.1% |
| LoRA 0-shot，前 100 句    | 44.71     | 40.26  | 42.37    | 0.3% | 0.1% |
| few-shot k=8，前 30 句    | 20.63     | 19.70  | 20.16    | 3.3% | 33.7% |

**关键观察：幻觉率与格式异常率是两个数量级的下降**（33.7% → 0.1%）。
说明 few-shot 阶段的很大一部分损失并非"不会抽实体"，而是**不会稳定输出合规格式**；
一旦用有监督信号把格式钉死，1.5B 基座也能达到可用水平。

### 6.3 与抽取式对照

| 范式                | 代表模型                  | Micro F1  |
| :---------------- | :-------------------- | :------- |
| 抽取式（BIO + softmax） | BERT                  | 76.18    |
| 抽取式（BIO + softmax） | MacBERT               | 76.58    |
| 生成式（LoRA SFT）      | Qwen2.5-1.5B          | **41.59** |
| 生成式（few-shot）      | Qwen2.5-1.5B          | 7.5–27.6 |

差距 34.6pp。**归因顺序**（报告/答辩口径）：
1. 基座规模差两个数量级（论文 GPT-3 175B vs 本项目 1.5B）；
2. 训练量悬殊：抽取式在全量 10,748 句上训练 3 epoch，生成式 LoRA 仅用 6,000 条样本 1 epoch；
3. 生成式需逐类型复制整句输出，10 类 × 1343 句 = 13,430 次生成，误差累积面更大。

## 7. 已知缺陷与后续可做的改进

1. **仍过预测约 2 倍**：全量 dev 预测 6,184 个实体 vs 金标 3,072 个。
   加 epoch / 加训练样本 / 提高负例占比（`--neg-per-sentence`）大概率还能涨。
2. **`micro` 与逐类型差异大**：`name` 62.16 而 `movie` 仅 7.49、
   `organization` 17.70——后两类本就是 CLUENER 的难点，抽取式同样偏低。
3. **截断风险**：few-shot 用 `--max-new-tokens 72/96`，长句会被截断。
   正式跑建议放宽到 128（代价是约 30% 的额外推理时间）。
4. **P2-2 低资源曲线**：本链路已具备 `limit` / `neg-per-sentence` 等控制旋钮，
   可直接做「训练规模 × 范式」对照，这是验证论文"少样本优势"主张最有说服力的一张图。
